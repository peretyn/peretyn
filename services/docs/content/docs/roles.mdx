---
title: Roles and permissions (RBAC)
description: Model roles and permissions (RBAC) with Peretyn, from global admins to per-project sharing.
---

You have checks like `if (user.role === 'admin')` scattered through your code. Peretyn replaces them with one call, `check`, and keeps the roles in one place.

You do not need to know ReBAC to do this. In Peretyn, a role is a relation, and a permission is computed from roles.

| RBAC word       | Peretyn word | Example                                       |
| --------------- | ------------ | --------------------------------------------- |
| role            | relation     | `admin`, `editor`, `viewer`                   |
| permission      | permission   | `can_edit`                                    |
| role assignment | tuple        | `user:grace` is `editor` on `project:billing` |
| has permission? | check        | `authz.check(...)`                            |

## Write the schema

This schema has three levels of roles: platform, organization and project. A project belongs to one organization, and the platform owns every project.

<include>../../snippets/roles/schema.ts</include>

Each layer works like this:

- **Global roles.** `platform` is a single object, such as `platform:main`. Its `admin` relation is the global admin role.
- **Organization roles.** `organization` has `admin` and `member`. An organization role applies to every project in the organization.
- **Project roles.** `project` has `admin`, `editor` and `viewer`. The `organization` and `platform` relations link a project to the objects it inherits roles from.
- **Inheritance.** `via('organization', 'admin')` means that an admin of the project's organization is an admin of the project. `via('platform', 'admin')` does the same for platform admins.
- **Permissions.** `can_manage` is granted to admins. `can_edit` is granted to editors and to anyone who can manage. `can_view` is granted to viewers, to anyone who can edit, and to organization members. So admin includes editor, and editor includes viewer.

## Check permissions

Ask for a permission, not a role. Your code does not need to know which role grants it:

<include>../../snippets/roles/check.ts</include>

The script prints:

```txt
ada can_manage project:billing: allowed
root can_manage project:docs: allowed
grace can_view project:billing: allowed
linus can_edit project:billing: denied
sam can_view project:docs: allowed
sam can_edit project:docs: denied
```

`ada` and `root` have no tuple on any project. Ada is an organization admin and Root is a platform admin, so both inherit `admin` on every project. Grace is an editor, so Grace can view. Linus is a viewer, so Linus cannot edit. Sam is an organization member, so Sam can view every project in the organization but edit none.

## Moving existing checks

Here is a typical role check:

```ts
function canEditProject(user: User, project: Project): boolean {
  if (user.role === 'admin') return true;
  if (project.admins.includes(user.id)) return true;
  return project.editors.includes(user.id);
}
```

With Peretyn, the function becomes a `check`. The role logic moves to the schema:

```ts
async function assertCanEditProject(userId: string, projectId: string): Promise<void> {
  await authz.assert({
    subject: { type: 'user', id: userId },
    relation: 'can_edit',
    object: { type: 'project', id: projectId },
  });
}
```

`assert` throws when the check is denied, so you can call it at the top of a handler. Use `check` when you want the boolean.

To keep the answers right, move the writes too:

- When you assign a role, write the tuple. This replaces setting `user.role` or pushing to `project.editors`.
- When you remove a role, delete the tuple.
- When you create a project, write its `organization` and `platform` tuples.

See [Tuples](/sdk/tuples) for `write` and `deletes`.
